EP.01 第一話

What I do

Multi-cloud data and AI architect. I pick the platform for the workload and the team, then build it. I've shipped on AWS, Azure and Google Cloud, and I design for portability where it pays off: open table formats, Spark, dbt and Terraform.

I stay hands-on, from the first architecture review to the pipeline in production.

  • MODE 01

    Cloud-native

    Use the provider's managed services fully when one cloud is the clear fit. Less to run, faster to ship.

  • MODE 02

    Cross-cloud

    One workload that spans providers, for example ingestion on one cloud and analytics on another, joined by open formats and data sharing.

  • MODE 03

    Multi-cloud

    Different workloads on different clouds, with shared governance, identity and cost reporting so the estate stays one system.

  • MODE 04

    Cloud-agnostic

    Logic that moves: Spark, dbt, Delta Lake or Iceberg, Terraform, and Databricks or Snowflake, which run on all three clouds.

  • MODE 05

    Migrations

    Lift-and-shift where speed matters, refactor where the cost or SLA case is clear. Warehouse to lakehouse is a common path.

  • MODE 06

    Greenfield

    From an empty account to the first production pipeline, with CI/CD, data quality checks and observability from day one.

CASE 01 · ENTERPRISE DATA PLATFORM

Cloud-native lakehouse on AWS + Databricks

Problem
Data spread across operational systems, with no single governed place for analytics or machine learning.
Architecture
Medallion layers (bronze, silver, gold) on Amazon S3 and Delta Lake. Kinesis for real-time ingestion, Redshift as the curated serving layer, Lake Formation for fine-grained access.
Outcome
One governed source for BI and ML, with streaming data landing next to batch.

FIG. 01 · reference flow

Architecture summary

Raw events and extracts land in bronze unchanged. Silver applies schema, deduplication and quality checks. Gold holds business-ready tables that feed Redshift for BI and Databricks for ML. Access is granted at table and column level through Lake Formation, not per bucket.

  • Amazon S3
  • Databricks
  • Delta Lake
  • Kinesis
  • Redshift
  • Lake Formation

CASE 02 · AGENTIC AI

Agentic AI platform with MCP

Problem
Teams wanted agents that answer from warehouse data and act on it, safely.
Architecture
Agent workflows on Amazon Bedrock using the Model Context Protocol. Tools on AWS Lambda query warehouses, generate reports and trigger downstream actions.
Outcome
Agents work from governed data through defined tools instead of ad-hoc database access.
  • Amazon Bedrock
  • MCP
  • AWS Lambda
  • Python

CASE 03 · MLOPS

MLOps pipeline on Databricks

Problem
Models trained by hand and hard to reproduce or retrain.
Architecture
MLflow experiment tracking, a Delta Lake feature store, automated retraining and CI/CD pipelines for model deployment.
Outcome
Repeatable training and deployment, with lineage from features to model.
  • Databricks
  • MLflow
  • Delta Lake
  • PySpark

CASE 04 · ANALYTICS

Snowflake analytics hub

Problem
Many teams needed the same data without copies or runaway compute bills.

Snowflake data sharing, dbt models, automated cost governance and a self-service analytics layer.
Outcome

EP.04 第四話

Open source, testing & benchmarks

FEATURED · APACHE-2.0 · v0.1.1

data-agent-gauntlet

An open-source harness that decides which AI coding agent to trust with your data platform.

Agents such as Claude Code and Kiro now write SQL and design warehouse tables. The gauntlet gives them real tasks on Amazon Redshift Serverless and lets the warehouse, not the agent, decide pass or fail.

  • 20 tasks, 5 categories on the TICKIT sample dataset: query 6, schema 4, loading 4, troubleshooting 4, optimization 2.
  • Graded by the platform. Checks compare results with reference queries, catalog state and S3 objects.
  • A/B by design. A baseline arm and a skills arm, for example with and without the aws-data-analytics plugin.
  • Measures the mistakes. Reads sys_query_history to count failed statements and PostgreSQL habits that break on Redshift.
  • Safe sandbox. Agent role scoped to one workgroup and one bucket, a daily cap (default 20 RPU-hours), one-command teardown.

Supports Claude Code and Kiro CLI today. Planned: more agents and platforms (Athena, Glue, S3 Tables), cost and token reporting, ranked verdicts.

BENCHMARK · AWS BUILDER CENTER · OCT 6, 2026

Apache Doris vs Athena vs Redshift Serverless

500 queries across five query patterns. Apache Doris 3.0 on one r6i.2xlarge, Redshift Serverless at 8 RPU, and Athena, over a 500M-row synthetic events table (about 420 GB uncompressed).

Point lookup p50 latency in the author's test setup
Enginep50
Apache Doris 3.08 ms
Redshift Serverless (8 RPU)450 ms
Athena2,100 ms

On full-table scans Doris was only 2x faster than Athena. On a 100-query burst Athena timed out and Doris averaged 94 ms. The conclusion was to run all three, each for the workload it suits.
